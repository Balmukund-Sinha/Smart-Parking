# SmartPark Intelligence: Student-Friendly Project Explanation

## 1. Project in one sentence

SmartPark Intelligence is a Big Data project that simulates parking sensors across the Mumbai Metropolitan Region, processes their events through Kafka and PySpark, stores useful results, predicts parking demand 30 minutes ahead, and displays everything in an interactive web dashboard.

## 2. What problem does this project solve?

In a busy city, drivers often spend time searching for a free parking space. This creates several problems:

- extra traffic near popular locations;
- wasted fuel and increased air pollution;
- delays for drivers;
- uneven use of parking facilities;
- difficulty for municipal operators to identify congestion early;
- no simple way to study historical demand or plan future capacity.

SmartPark collects parking events, calculates the latest occupancy of each parking zone, finds zones with available bays, studies past demand, and predicts future occupancy. An operator can use this information to guide vehicles toward a less crowded parking facility.

## 3. Main objectives

The project was built to demonstrate how the following parts work together:

1. Generate parking telemetry similar to IoT sensor messages.
2. Ingest a continuous event stream with Apache Kafka.
3. Validate, deduplicate, and aggregate events with PySpark Structured Streaming.
4. Store raw and processed information in Parquet files and PostgreSQL.
5. Train a machine-learning model to predict occupancy 30 minutes ahead.
6. Show live, historical, geospatial, machine-learning, and system-health information in one dashboard.
7. Provide a project that can be demonstrated on Windows without installing native Hadoop binaries.

## 4. Important note about the data

The historical parking-event data in this repository is **synthetically generated for education and demonstration**. Hybrid mode can additionally accept real operator observations and fetch public live context, and the interface labels each source.

- It is not an official feed from the Mumbai municipal authorities.
- It does not contain real vehicle registrations or personal information.
- Zone names and Mumbai-area coordinates make the demonstration geographically meaningful.
- Occupancy, vehicle IDs, parking durations, weather, ENTRY events, and EXIT events are generated by the project.
- OpenStreetMap supplies the background map tiles when an internet connection is available.
- Open-Meteo supplies current Mumbai weather; OpenStreetMap Overpass supplies real mapped parking-facility locations.
- Neither public source supplies reliable bay occupancy. Actual occupancy must come from a sensor/Kafka event or an operator observation in the Parking Map.

This approach makes the project repeatable, safe to share on GitHub, and usable without access to private IoT hardware or government data.

## 5. Where does the data come from?

The project has two related data paths.

### 5.1 Historical data path

The script `scripts/generate_dataset.py` creates a realistic historical dataset. It simulates:

- 20 parking zones in the Mumbai Metropolitan Region;
- zone names, locations, and capacities;
- vehicle arrivals and departures;
- parking duration;
- occupancy changes;
- temperature and rainfall;
- weekday, weekend, and holiday patterns.

It produces these important files:

| File | Purpose |
|---|---|
| `data/raw/zones.csv` | Master list of parking zones, capacities, and coordinates |
| `data/raw/parking_events.csv` | Full generated history of ENTRY and EXIT events |
| `data/sample/parking_events_sample.csv` | Small sample that is easy to inspect |
| `data/processed/ml_dataset.csv` | Time-based features and the future-occupancy target used for model training |
| `data/processed/dashboard_data.csv` | Prepared operational values for dashboard views |
| `data/processed/occupancy_trend.csv` | Historical occupancy trend data |

The generator uses a fixed random seed so that the dataset can be reproduced. It also uses realistic time patterns, such as different demand during morning, afternoon, and evening periods.

### 5.2 Live streaming path

The script `kafka/producer.py` behaves like a group of IoT parking sensors. It continuously sends generated parking events to the Kafka topic named `parking-events`.

Each event contains fields similar to the following:

```json
{
  "event_id": "a-unique-uuid",
  "timestamp": "2026-09-23T12:00:00",
  "vehicle_id": "V01234",
  "zone_id": "Z003",
  "event_type": "ENTRY",
  "parking_duration": 0,
  "occupancy": 43,
  "capacity": 108,
  "latitude": 19.0935,
  "longitude": 72.8565,
  "temperature": 29.4,
  "rainfall": 2.1
}
```

The producer keeps occupancy within sensible limits: it cannot go below zero or above the declared capacity of a zone.

### 5.3 Operational and system data

The dashboard also reads technical status from the local project environment:

- Docker container state;
- Kafka topic position and throughput;
- recent Spark micro-batch timing;
- Parquet file counts;
- PostgreSQL readiness;
- generated model metrics and predictions.

These values explain whether the demonstration pipeline is healthy. They are not municipal production-service metrics.

## 6. Complete data flow

```text
Historical dataset generator                 Live event producer
          |                                          |
          |                                          v
          |                              Kafka topic: parking-events
          |                                          |
          |                                          v
          |                              PySpark Structured Streaming
          |                         validate -> deduplicate -> aggregate
          |                                          |
          |                              +-----------+-----------+
          |                              |                       |
          v                              v                       v
Raw/processed CSV files          Bronze Parquet events   Silver Parquet metrics
          |                              |                       |
          +------------------------------+-----------------------+
                                         |
                           +-------------+-------------+
                           |                           |
                           v                           v
                 Random Forest training       PostgreSQL serving tables
                           |                           |
                           +-------------+-------------+
                                         |
                                         v
                              Integrated web dashboard
```

In simple words:

1. The producer creates an event.
2. Kafka safely receives and buffers the event.
3. Spark reads events in small batches.
4. Spark rejects invalid records and detects duplicates.
5. Clean events are stored in the Bronze layer.
6. Five-minute zone summaries are stored in the Silver layer.
7. Historical features train the Random Forest model.
8. PostgreSQL keeps compact tables for operational queries.
9. The frontend combines these sources into understandable pages.

## 7. Technologies used and why they were selected

### Python

Python is used for data generation, Kafka production, streaming logic, machine learning, database loading, backend integration, and testing.

Why it was used:

- easy for students to read;
- strong data-science libraries;
- good Kafka, Spark, PostgreSQL, and machine-learning support;
- allows most of the project to use one programming language.

### Pandas and NumPy

Pandas manages tabular data, while NumPy supports numerical and random-data operations.

Why they were used:

- fast dataset preparation;
- simple CSV and Parquet handling;
- convenient grouping, filtering, and feature engineering;
- useful offline fallback when Spark is not required.

### Apache Kafka

Kafka is the event-ingestion and buffering layer. The producer writes events to `parking-events`, and Spark reads from that topic.

Why it was used:

- producers and consumers do not need to run at exactly the same speed;
- events can be replayed from stored offsets;
- it is designed for high-throughput streaming systems;
- it demonstrates a standard Big Data ingestion architecture.

This project uses Kafka in KRaft mode, so ZooKeeper is not required.

### PySpark Structured Streaming

Spark processes the Kafka stream as a sequence of small micro-batches.

Why it was used:

- schema-based validation;
- time-window aggregation;
- watermark handling for late events;
- scalable processing model;
- direct integration with Kafka and Parquet.

The stream uses a five-minute watermark and five-minute zone windows. A watermark tells Spark how long it should continue accepting late events before old state can be cleaned up.

### Bloom filter

A Bloom filter is a memory-efficient probabilistic data structure used to check whether an event ID has probably been seen before.

Why it was used:

- duplicate checks are very fast;
- it uses much less memory than keeping every ID in a normal set;
- it demonstrates an important Big Data data-structure concept.

The implementation uses a 2,000,000-bit vector and six hash probes. A Bloom filter does not produce false negatives for inserted items, but it can produce a false positive: a new ID can rarely be classified as already seen. A safety-critical production system would pair this with an exact durable ID store or another idempotency method.

### Parquet and the Bronze/Silver lakehouse pattern

Parquet is a compressed column-oriented file format.

- **Bronze** stores validated event-level records close to their original form.
- **Silver** stores cleaned and aggregated five-minute zone metrics.

Why Parquet was used:

- analytical queries can read only the required columns;
- compression reduces storage;
- date and zone partitions reduce unnecessary scanning;
- both Spark and Pandas can read it.

### PostgreSQL

PostgreSQL is the operational serving database. The project creates tables for parking zones, occupancy summaries, and predictions.

Why it was used:

- structured SQL queries;
- reliable relational constraints;
- fast access to compact operational results;
- separates dashboard-serving data from the large event history.

The database loader prepares PostgreSQL from the generated and processed files. The full event lake remains in Parquet rather than being copied entirely into PostgreSQL.

### Random Forest regression

The machine-learning model is a scikit-learn `RandomForestRegressor`. It combines predictions from many decision trees.

Why it was used:

- works well with non-linear relationships;
- handles different feature scales without complex preprocessing;
- is more resistant to overfitting than a single decision tree;
- provides feature importance for explanation;
- is suitable for a clear college-level demonstration.

The trained model is saved with Joblib so that the dashboard can load it without retraining every time.

### Leaflet and OpenStreetMap

Leaflet displays the interactive browser map, and OpenStreetMap supplies map tiles.

Why they were used:

- open and widely used mapping tools;
- support markers, popups, zooming, and geographic layers;
- no proprietary map key is required for the basic map.

### HTML, CSS, JavaScript, and the integration server

The frontend uses browser-native technologies and is served by `Frontend/server.py`.

Why they were used:

- responsive and interactive interface;
- direct control over the design;
- live API polling, charts, tables, filters, and downloads;
- one integrated local application for all eight pages.

### Docker Compose

Docker runs Kafka, Spark, and PostgreSQL in Linux containers.

Why it was used:

- consistent setup on different computers;
- isolates dependencies;
- avoids native Windows Hadoop problems such as `winutils.exe`, DLL loading, and temporary JAR locking;
- makes services easier to start and stop together.

### Pytest

Pytest verifies important project behavior.

Why it was used:

- catches regressions;
- checks backend endpoints and data logic;
- gives evidence that the repository works after changes.

## 8. How stream processing works

### Step 1: Kafka receives an event

The event producer serializes a Python dictionary as JSON and sends it to `parking-events`.

### Step 2: Spark applies a schema

Spark converts JSON fields to known data types. Records missing important values such as `event_id`, `timestamp`, `occupancy`, or `capacity` are rejected.

### Step 3: Duplicate detection

The Bloom filter checks the event ID. Probable duplicates are removed before expensive downstream work.

### Step 4: Event-level storage

Valid events are appended to Bronze Parquet files. This gives the project an inspectable history.

### Step 5: Window aggregation

Spark groups records by zone and five-minute event-time window. It calculates values such as:

- average occupancy;
- maximum occupancy;
- average capacity;
- number of events;
- utilization percentage.

### Step 6: Aggregate storage

The calculated metrics are written to the Silver layer for analytics and dashboard use.

## 9. How the prediction model works

### 9.1 Prediction question

The model answers:

> Based on current conditions, how many parking bays are likely to be occupied 30 minutes from now?

### 9.2 Input features

The model uses nine features:

1. hour of day;
2. day of week;
3. whether the day is a weekend;
4. whether the day is a holiday or major event;
5. temperature;
6. rainfall;
7. current occupancy;
8. zone capacity;
9. average parking duration.

### 9.3 Target

The target column is `future_occupancy`, created by shifting each zone's time-bucketed occupancy forward by 30 minutes.

### 9.4 Training process

- 80% of the prepared rows are used for training.
- 20% are used for testing.
- The model uses 200 decision trees.
- A fixed random state makes results repeatable.
- The trained artifact is written to `ml/model.pkl`.
- Feature importance and held-out predictions are also exported.

### 9.5 Evaluation metrics

| Metric | Simple meaning | Better direction |
|---|---|---|
| MAE | Average absolute difference between actual and predicted occupied bays | Lower |
| RMSE | Similar to MAE but penalizes large mistakes more strongly | Lower |
| R-squared | Fraction of variation explained by the model | Closer to 1 |

The exact values shown in the UI come from the current trained artifact. Metrics can change when the dataset or model is retrained.

The prediction is decision support, not a guarantee. Sudden road closures, concerts, sensor failures, or unusual behavior may cause actual demand to differ.

## 13. Important calculations and concepts

### Utilization

```text
utilization (%) = occupied bays / total capacity x 100
```

### Available bays

```text
available bays = capacity - occupancy
```

### Little's Law in data generation

The generator uses the relationship:

```text
average vehicles in system = arrival rate x average stay duration
```

This helps generated arrivals, parking duration, and occupancy remain related instead of being completely random.

### Event time and processing time

- **Event time** is when the parking event says it occurred.
- **Processing time** is when Spark actually handles it.

Using event time and a watermark makes the system more tolerant of delayed messages.

### Consumer lag

Consumer lag is the difference between the latest Kafka offset and the last processed offset. A growing lag can mean the consumer is slower than the producer.

### Partitioning

Parquet data can be divided by date and zone. A query for one date or zone can skip unrelated files, reducing scan cost.

## 15. Demo mode and full-pipeline mode

### Dataset or offline-style mode

The generator creates the files needed by most analytical and machine-learning views. This is useful when Docker is unavailable or when a student only needs a repeatable dashboard demonstration.

### Full-pipeline mode

Kafka, the continuous producer, Spark, PostgreSQL, and the frontend run together. This mode demonstrates real stream movement, offsets, micro-batches, Parquet output, and service diagnostics.

The interface should label unavailable dependencies honestly. A stopped Kafka or PostgreSQL service must not be displayed as healthy merely because old files exist.

## 16. Limitations

This is an educational prototype, so it has important limitations:

- data is generated rather than captured from installed parking sensors;
- map drive-time estimates are not based on live road traffic;
- weather values are simulated;
- the default deployment runs on one computer rather than a multi-node cluster;
- the model is trained on synthetic patterns and is not validated for real public decisions;
- a Bloom filter can create rare false positives;
- authentication and role-based access would be needed for a public production system;
- long-term production monitoring, backups, encryption, and disaster recovery are outside the current scope.

## 18. Privacy, security, and responsible use

- Generated vehicle IDs are fictional.
- No real person's movement should be published from this project.
- Production vehicle identifiers should be minimized, encrypted, or pseudonymized.
- Database credentials belong in environment variables, not committed source files.
- Public deployments need HTTPS, authentication, authorization, audit logs, and rate limits.
- Forecasts should assist human decisions rather than automatically penalize users or restrict access.

## 19. Common viva questions and short answers

### Why use Kafka instead of writing every event directly to a database?

Kafka buffers events, separates producers from consumers, supports replay through offsets, and handles streaming throughput more naturally.

### Why use Spark if Pandas can process the demo dataset?

Pandas is convenient on one machine, while Spark demonstrates distributed, stateful, event-time stream processing that can scale to larger workloads.

### Why use both Parquet and PostgreSQL?

Parquet is efficient for large analytical history. PostgreSQL is useful for smaller structured serving tables and low-latency operational queries.

### Why use a Bloom filter?

It checks duplicate IDs using a small fixed amount of memory. The trade-off is a small possibility of false positives.

### What is a watermark?

It defines how late an event may arrive before Spark considers an old time window complete and releases its state.

### What does the Random Forest predict?

It predicts the number of occupied bays in a selected parking zone 30 minutes in the future.

### Is the map using real live parking data?

No. It uses Mumbai-area locations with synthetically generated parking telemetry. OpenStreetMap provides the real geographic basemap.

### Is this really scalable?

The local workload is intentionally small, but Kafka, Spark, Parquet partitioning, and separated serving layers are scalable architectural patterns.

### Why run Spark in Docker on Windows?

The Linux container includes the expected Java, Spark, and Hadoop environment and avoids common native Windows `winutils.exe`, DLL, and file-locking issues.

### What happens if Kafka stops?

No new events are received. The dashboard can still show stored historical data, but health indicators should report that streaming is degraded.

## 22. Final summary

SmartPark Intelligence demonstrates a complete path from a simulated parking sensor event to a useful operator decision. Kafka handles ingestion, Spark performs streaming validation and aggregation, the Bloom filter reduces duplicates, Parquet stores analytical history, PostgreSQL serves compact operational data, Random Forest predicts near-future demand, and the web interface turns technical results into maps, charts, tables, alerts, and actions.

Its main educational value is not only the dashboard. The project shows why each layer exists, what responsibility it owns, how the layers exchange data, and what trade-offs must be considered before converting a classroom prototype into a real city system.
