# SmartPark Website Page Guide

This guide explains every page of the SmartPark Intelligence website in simple words. It explains what each card, chart, number, status, filter, and button means.

## 1. What is this website for?

SmartPark is a control dashboard for parking facilities in the Mumbai Metropolitan Region (MMR). It brings together:

- parking events such as vehicle entry and exit;
- current occupied and free parking bays;
- a real map of Mumbai-area parking locations;
- historical demand patterns;
- 30-minute demand predictions;
- Kafka, Spark, PostgreSQL, and Parquet pipeline information;
- system health and diagnostics.

The project is educational. Most parking events are generated by the project so that the full Big Data pipeline can be demonstrated without physical sensors. Hybrid mode can also use public weather and map information and accept operator-entered occupancy observations.

## 2. Parts shared by every page

### Left navigation dock

The menu on the left opens the eight main pages:

1. Overview
2. Live Monitoring
3. Parking Map
4. Historical Analytics
5. Demand Prediction
6. Big Data Pipeline
7. Data Explorer
8. System Health

The highlighted menu item is the page that is currently open.

### Stream Engine status

The box at the bottom of the left dock shows the general pipeline state.

- **OK or Active** means the available services are responding.
- **Degraded** means one or more services need attention.
- **Offline** means the integration API or an important live service cannot be reached.

The text below the status lists the services being checked, such as Kafka, Spark, and PostgreSQL.

### Collapse Dock

This hides the left menu to give the page more horizontal space. When it is collapsed, the reopen control remains available so the menu can be shown again.

### Top header

The top header stays consistent on every page.

- **Mumbai Metropolitan Region** shows the selected city or operating area.
- **All 20 Zones** shows the current parking-zone scope.
- **Live Window / History Window** shows the time period used by the page.
- **LIVE and ev/s** show whether live updates are available and the recent event rate.
- **IST clock** shows the current Indian Standard Time used by the dashboard.
- **Bell icon** opens page-related alerts or service information.

### Common colours

- **Green** means normal, available, healthy, running, or successful.
- **Cyan/blue** means live information, a selected item, or a normal information value.
- **Amber/yellow** means medium risk or something that should be watched.
- **Red** means critical risk, failure, offline, or an action that needs attention.
- **Purple** is mainly used for model evidence or an additional chart series.

### Important words

- **Occupancy**: number of bays currently being used.
- **Capacity**: total number of bays in a parking zone.
- **Available bays**: capacity minus occupancy.
- **Utilization**: occupancy shown as a percentage of capacity.
- **Dwell time**: how long a vehicle stays parked.
- **Throughput**: how many events are handled in one second.
- **Telemetry**: measurements and status information sent by sensors or software.

## 3. Overview page

**Address:** `/overview`

### Main purpose

The Overview page is the control-room summary. It answers these questions quickly:

- How full is the complete parking network?
- How many bays are free?
- Are all zones sending data?
- Is any zone likely to become crowded?
- Is the data pipeline working?

### AI Dispatch Advisory

This message highlights an important parking situation. It can show crowded zones, the expected time of saturation, and a recommended alternative zone with more free bays.

- **Apply Smart Reroute** records or prepares the suggested rerouting action.
- **Dismiss** hides the current advisory from the screen.

The recommendation is decision support. A human operator should still consider road conditions and local rules.

### Summary cards

#### MMR Occupancy

Shows the percentage of all parking bays currently occupied across the selected zones. It also shows the occupied-bay count and total capacity.

#### Available Bays

Shows how many parking bays are currently free. The small bar compares used space with free space.

#### Zone Heartbeat

Shows how many monitored parking zones are responding. For example, `20/20` means all 20 zones have recent information.

#### Events Ingested

Shows the total number of source events available to the project. The smaller value shows the recent event rate.

#### 30-Minute ML Risk Hubs

Shows how many zones are predicted to cross the critical utilization level during the next 30 minutes.

#### Median Dwell

Shows the middle parking-stay duration. Half of completed stays were shorter than this value, and half were longer.

### Geospatial telemetry map

This is a real OpenStreetMap map of the Mumbai region. Each zone marker shows its zone ID and utilization.

- Green markers represent normal utilization.
- Cyan markers represent moderate utilization.
- Red markers represent critical utilization.
- Clicking a marker opens that zone's details.

The zone detail card shows current occupancy, model forecast, mean dwell time, weather, and the data source.

### Zone Risk Leaderboard

Ranks zones from the highest utilization to the lowest.

- Search filters the list by zone ID or zone name.
- All, Critical, Moderate, and Normal buttons filter by risk group.
- Each progress bar compares occupied bays with total capacity.
- Export downloads zone information as GeoJSON or CSV.

### 24-Hour Demand: Actual vs ML

Compares recent real/observed occupancy with the machine-learning forecast.

- The solid line is the observed value.
- The dashed line is the predicted value.
- R² shows how much variation the model explains. A value closer to 1 is generally better.

### Hub Capacity Pressure

Lists the most heavily used parking zones. Each row shows occupied bays, capacity, utilization, and available space.

### Dynamic Flow Delta

Compares vehicle entries with vehicle exits.

- Positive/green flow means more vehicles are entering than leaving.
- Negative/red flow means more vehicles are leaving than entering.
- Net flow helps explain whether occupancy is likely to rise or fall.

### Big Data Telemetry Architecture

Shows the major data stages from sensor events to the operator dashboard. It is a quick visual explanation of Kafka ingestion, Spark processing, deduplication, Parquet storage, machine learning, and the command centre.

## 4. Live Monitoring page

**Address:** `/live-monitoring`

### Main purpose

This page shows recent Kafka parking events and explains how duplicate messages are removed before storage.

### Sensor backbone bar

Shows the Kafka broker state, current topic, broker offset/position, and whether live ingestion is running.

### Live Ingestion button

Pauses or resumes updates in the browser. Pausing the screen does not delete Kafka data.

### Refresh interval buttons

The `1s`, `2s`, and `5s` controls decide how often the browser asks the backend for newer information. A shorter interval updates faster but makes more requests.

### Purge Buffer

Clears only the event rows held in the current browser view. It does not delete events from Kafka, Parquet, or the raw dataset.

### Export Stream

Downloads the event view as CSV or JSON.

### Live metric cards

#### Ingestion Velocity

Recent number of events received per second.

#### Micro-Batch Latency

Time taken by the latest Spark micro-batch. If this becomes much higher than the trigger interval, processing may be falling behind.

#### Consumer Lag

Difference between the newest Kafka message and the last processed message. Zero is ideal because it means the consumer has caught up.

#### Deduplication Purge

Number of repeated event IDs rejected by the Bloom filter.

#### Late Watermark

Maximum allowed event lateness. Spark uses this to decide how long it should wait for delayed events.

### Bloom Filter Ingestion Pipeline

Explains the three duplicate-detection steps:

1. **Ingress** receives an event ID.
2. **Hashing Array** calculates several positions inside the bit vector.
3. **Decision Gate** accepts a new event or rejects a probable duplicate.

### Bit Vector Saturation

Shows how much of the Bloom filter memory has been used. A very full bit vector increases the chance of false positives and may need to be reset or expanded.

### Bloom filter counters

- **Total checked**: all event IDs tested.
- **Accepted**: new events allowed into downstream processing.
- **Purged duplicates**: repeated events removed.
- **Memory**: amount of memory reserved for the Bloom filter.

A Bloom filter guarantees no false negatives for inserted items, but it can very rarely report a new item as already present.

### Event filter bar

- Search by vehicle ID or event UUID.
- Select a Mumbai zone.
- Filter ENTRY, EXIT, or duplicate events.
- Filter by verification/pipeline status.

### Event table

Each row contains:

- event UUID;
- timestamp in IST;
- zone and facility;
- generated vehicle registration;
- ENTRY or EXIT type;
- zone occupancy;
- sensor and weather information;
- pipeline status;
- row actions.

Previous and Next move through the buffered event pages.

### Kafka Partition Lag Distribution

Shows each topic partition, its current offset, and its lag. A partition is one ordered section of a Kafka topic.

### PySpark Micro-Batch Execution

Shows recent Spark batch durations. It helps identify slow processing or unstable batch times.

## 5. Parking Map page

**Address:** `/parking-map`

### Main purpose

This page answers: “Where are the parking zones, which zones have space, and where should a vehicle be redirected?”

### Data source status

The page clearly labels the source of the selected zone:

- **Kafka** means a recent streaming event is available.
- **Operator observation** means a person recorded the occupancy.
- **Bronze/Parquet** means the latest stored pipeline record is being used.
- **Stored snapshot** means the page is using generated or previously saved data.

### Sync Live Sources

Requests the available hybrid sources again. This can refresh public weather, mapped parking facilities, and other supported live context. Public map services do not provide reliable live bay occupancy.

### Find Best Available Hub

Selects a suitable zone using availability and distance. It is a recommendation, not a guaranteed road route.

### Export GeoJSON

Downloads map-ready geographic data containing zone locations and properties.

### Search and filter controls

- Search finds a zone by ID or name.
- Map, Split, Grid, and Satellite change the presentation where supported.
- All Zones shows every zone.
- High Vacancy shows zones with many free bays.
- Moderate shows zones with 10 to 40 free bays.
- Critical Risk shows zones at or above the critical utilization threshold.
- Heatmap, Zone Nodes, and Risk Isobars toggle map layers.

### Map controls

- `+` zooms in.
- `−` zooms out.
- The location control returns to the operating region.
- Fullscreen expands the map.
- Clicking a zone marker selects it and opens its detail panel.

### Selected zone panel

#### Occupied

Current number of used bays.

#### Available

Current free bays and the free-space percentage.

#### Mean Dwell

Average or typical historical stay time.

#### Current Capacity Pressure

Progress bar showing how full the selected zone is.

#### 30-Minute Forecast

Shows the model's predicted utilization, predicted occupied bays, predicted free bays, and expected change from the current value.

#### Suggested Reroute Alternatives

Ranks nearby facilities by free bays and estimated distance/time. Travel time is an estimate based on geography, not live traffic routing.

### Live occupancy observation

When available, the operator controls can record a real observation:

- **Vehicle entry** adds one occupied bay.
- **Vehicle exit** removes one occupied bay.
- **Set occupancy** records the exact entered value.

Occupancy is kept between zero and the zone's capacity.

### Record VMS Guidance

Records a Variable Message Sign guidance action for the selected reroute. It represents what could be sent to a roadside display or operator system.

### Download Zone JSON

Downloads the selected zone's current details in JSON format.

### Bottom network summary

Shows total system capacity, total free bays, high-risk zone count, ingress speed, map-source state, and active cluster name.

## 6. Historical Analytics page

**Address:** `/historical-analytics`

### Main purpose

This page studies past parking behaviour. It helps find busy hours, long stays, weather effects, repeated congestion, and capacity pressure.

### Date controls

- **7D** loads seven days.
- **14D** loads fourteen days.
- **30D** loads thirty days.
- **Quarter** requests ninety days.
- **Custom** accepts a period from 1 to 120 days.

If less history exists than requested, the page shows the actual available coverage instead of pretending that the complete period exists.

### Resolution

Controls how detailed the time groups are. Hourly resolution combines smaller records into hourly values, making long periods easier to read.

### Compared zones

The zone chips show which facilities are included in the comparison.

- `×` removes one zone.
- **Compare zone** adds another zone.
- At least one zone must remain selected.

### Metric tabs

#### Occupancy %

Shows how full each zone was.

#### Inflow/Outflow Volume

Shows ENTRY and EXIT counts over time.

#### Turnover Rate

Shows entries plus exits as a percentage of capacity. Higher turnover means bays are changing users more frequently.

#### Revenue

Shows an educational estimate using a fixed value per exit. It is not an official financial record.

### Summary cards

- **Filtered Events**: number of event records used after filters.
- **Mean Utilization**: average occupancy percentage across selected zones.
- **Average Dwell**: average completed parking duration.
- **Peak Congestion**: busiest day and hour in the selected data.
- **Estimated Revenue**: analytical revenue estimate for the filtered records.

### Multi-Zone Occupancy Timeline

Line chart comparing the selected zones over time. Each colour represents one zone.

### Congestion by Day and Hour

A 7 × 24 heatmap. Rows represent days of the week and columns represent hours. Brighter cells mean greater utilization.

### Dwell Time Distribution

Groups completed parking sessions into duration ranges such as 0–15 minutes, 1–2 hours, or 4+ hours. It also shows the median and mean stay.

### Weather vs Occupancy

Plots rainfall against utilization. It helps explore whether rainy periods in this dataset are linked to different parking demand. Correlation does not prove that rain alone caused the change.

### Capacity vs Utilization

Ranks the most pressured zones and compares their utilization with total bays.

### Sync Lakehouse Partition

Refreshes the analytics data from the latest available lakehouse partition.

### Export Analytics

Exports the selected analytical view as PDF, CSV, Parquet, or a LaTeX viva brief.

### PySpark Job Spec and Viva Brief

These evidence tools explain the aggregation logic and create a student-friendly technical summary for a project presentation.

## 7. Demand Prediction page

**Address:** `/demand-prediction`

### Main purpose

This page predicts how many bays may be occupied 30 minutes from now. It also lets the user compare three real models.

### Model selector

#### RF v3.2

Random Forest combines many decision trees. It handles non-linear patterns well and provides feature importance.

#### XGBoost v1.8

XGBoost builds trees in sequence. Each new tree tries to correct errors made by earlier trees.

#### Linear Baseline

Linear Regression is a simpler and easier-to-explain comparison model. It shows whether the more advanced tree models provide a useful improvement.

Selecting a model changes:

- live inference;
- MAE, RMSE, and R² cards;
- actual-versus-predicted chart;
- feature importance;
- 30-minute zone-risk results;
- model card and exports.

### Model quality cards

#### R² coefficient

Shows how much variation is explained by the model. Closer to 1 is usually better.

#### MAE error

Average absolute prediction error in bays. Lower is better.

#### RMSE dispersion

Another error value that penalizes large mistakes more strongly. Lower is better.

#### Lookahead Horizon

The model predicts 30 minutes into the future.

#### Training Sample

Number of typed analytical rows used by the training workflow.

### Scenario presets

- **Heavy monsoon** fills inputs with heavy-rain conditions.
- **Wankhede match** represents a large venue event.
- **Diwali festival** represents holiday/event demand.
- **Weekday evening** represents normal evening traffic.

These presets only fill the controls. The user can still change every value before running inference.

### Inference inputs

- **Target municipal zone** selects the facility.
- **Simulation hour** sets the hour of day.
- **Day of week** sets Monday to Sunday.
- **Rainfall** sets rain in millimetres.
- **Temperature** sets degrees Celsius.
- **Current occupancy** sets occupied bays now.
- **Average dwell** sets the expected parking duration.
- **Commercial event factor** marks a holiday or major event.

### Run ML Inference

Sends the chosen values to the selected model and returns a 30-minute forecast.

### Projected Saturation Outcome

Shows:

- predicted occupied bays;
- predicted available bays;
- predicted utilization;
- LOW, MEDIUM, or HIGH risk;
- 95% confidence interval;
- expected increase or decrease;
- a possible alternative facility.

A confidence interval is an uncertainty range, not a guarantee.

### 24-Hour Occupancy: Actual vs Forecast

Compares actual targets with predictions saved for the selected model. The confidence band shows approximate uncertainty around the forecast.

### Feature Importance

Ranks the nine model inputs by their contribution. Random Forest and XGBoost use tree importance. Linear Regression uses normalized coefficient influence.

Importance does not prove that a feature caused demand; it only describes how the trained model used it.

### Cross-Metropolitan Saturation Risk

Shows the latest selected-model forecast for the most important zones and labels each one as normal, moderate, or critical.

### Run Benchmark

Compares Random Forest, XGBoost, and Linear Regression on the same saved validation rows. Using the same rows makes the comparison fair.

### Open Model Card

Shows model version, framework, target, training rows, feature contract, prediction horizon, and risk thresholds.

### Export Model

Downloads the selected model's metadata as JSON or a PMML interoperability manifest.

## 8. Big Data Pipeline page

**Address:** `/big-data-pipeline`

### Main purpose

This page explains how one parking event travels through the project. It is useful for debugging and for a college viva.

### Pipeline metric cards

- **End-to-End Latency**: estimated time from sensor event to dashboard response.
- **Throughput Rate**: recent number of events processed per second.
- **Kafka Position**: current message position/offset.
- **Bloom Bits Set**: number and percentage of Bloom filter bits in use.
- **Micro-Batch Interval**: time taken by the latest Spark batch.
- **ML Inference R²**: current model validation score.

### Interactive Stream Processing Canvas

Shows eight stages:

1. IoT Ground Nodes
2. Kafka Broker
3. PySpark Stream
4. Bloom Deduplication
5. Parquet Lakehouse
6. PostgreSQL Serving
7. ML Model Ingress
8. Command and Road VMS

Each stage shows its responsibility, technology, running state, and current metric. Clicking a stage explains it in more detail.

### Status meanings

- **Running** means the stage is available.
- **Attention** means the stage is unavailable or showing a warning.
- The running counter shows how many of the eight stages are healthy.

### Simulate Event Pulse

Sends one test parking event through Kafka when Kafka is available. This is useful for demonstrating live movement.

### Pause Animation

Stops only the visual animation. It does not stop Kafka or Spark.

### Spark DAG

Shows the Directed Acyclic Graph explanation of Spark operations. A DAG is the ordered plan Spark follows to transform data.

### Export Defense PDF

Downloads a PDF summary of the architecture and stage status.

### Event Journey Inspector

Follows one recent event through the eight stages. Each row shows the stage time, state, and cumulative time from the original event.

### Latency Stack

Breaks total latency into sensor, Kafka, Spark, Bloom filter, Parquet, PostgreSQL, machine learning, and dashboard portions.

Some values are observed directly, while very small stages may use clearly labelled estimates.

### Latest Stored Payload

Shows the newest event as JSON. This helps students understand the fields received by the pipeline.

### College Project Viva & Architecture Defense

Explains:

- why Kafka and Spark are used together;
- why a Bloom filter is used;
- why Parquet is partitioned.

### Download Evidence JSON

Downloads architecture evidence and current pipeline measurements in a machine-readable file.

## 9. Data Explorer page

**Address:** `/data-explorer`

### Main purpose

This page safely inspects the datasets created by the project. It is similar to a small lakehouse catalogue and governed query tool.

### Catalogue summary cards

- **Catalogue Rows**: total records across registered datasets.
- **Bronze Events**: validated event-level records.
- **Silver Features**: cleaned/model-ready analytical rows.
- **Parquet Lake**: number of Parquet partitions/files.
- **Data Quality**: percentage of checked records that satisfy the required rules.

### Lakehouse Catalog

The selectable datasets include:

- **Bronze Raw Events**: validated source events.
- **Zone Registry**: zone names, coordinates, and capacities.
- **Silver ML Features**: prepared model features.
- **Gold Predictions**: trained model results.
- **Serving Dashboard**: compact records used by the UI.

Selecting a dataset updates the schema, query template, row count, and data preview.

### Raw Schema

Lists every field, its inferred data type, and whether it is required. Examples include event ID, timestamp, vehicle ID, zone ID, occupancy, capacity, temperature, and rainfall.

### Safe SQL Query Console

Runs approved analytical templates. It intentionally does not run arbitrary shell commands or unrestricted SQL.

- Choose a query template.
- **Execute query** runs the approved query.
- Returned-row count shows the result size.
- Query time shows how long it took.
- Partition count shows how much data was scanned.

### Filter current dataset

Searches visible records across the available fields.

### Table Grid and JSON Dump

- **Table Grid** shows rows and columns.
- **JSON Dump** shows the same records as JSON.
- **Previous** and **Next** move between result pages.

### Recent Parquet Partitions

Lists recently created files, their size, and time. Parquet is a compressed column-based format used for analytics.

### Data Quality Scorecard

Checks:

- timestamp completeness;
- event-ID uniqueness;
- occupancy range validity;
- required schema fields.

### Sync Metastore

Refreshes the list of datasets, schemas, and row counts from available project files.

### SQL Console

Scrolls directly to the governed query section.

### Export Parquet

Downloads the selected dataset in Parquet format.

### DDL Schema

Downloads SQL Data Definition Language describing the selected schema.

### Export Schema Evidence

Downloads schema information that can be used in the project report or viva.

## 10. System Health page

**Address:** `/system-health`

### Main purpose

This page answers: “Are Docker, Kafka, Spark, PostgreSQL, the API, and the Parquet lake working correctly?”

### Health summary cards

- **Cluster SLA**: percentage of required checks currently passing.
- **Ingestion Velocity**: recent Kafka event rate.
- **PySpark Cadence**: latest Spark micro-batch interval.
- **Kafka Position**: current committed topic offset.
- **Parquet Lake**: number of indexed Bronze files.

### Container Orchestration Matrix

Lists every Docker Compose service and shows:

- service name;
- running state;
- process/health state;
- runtime or uptime.

### Service Readiness

Runs separate checks for:

- Docker Engine;
- Kafka broker;
- PySpark stream;
- PostgreSQL;
- Parquet lake.

A green check means that dependency responded successfully.

### Safe Diagnostic Console

The dropdown offers approved checks only:

- Full health
- Kafka offsets
- PostgreSQL readiness
- Parquet inventory

**Execute** runs the selected safe diagnostic. It never runs arbitrary text as a shell command.

### Kafka & Stream Telemetry

Shows partition offset, recent throughput, peak throughput, API uptime, and synchronization state.

### Live Cluster Telemetry Stream

Shows structured log messages from the integration API, Docker discovery, Kafka, Spark, PostgreSQL, and Parquet checks.

### Run Health Check

Immediately refreshes every readiness check and updates the page.

### Recover Degraded Services

First checks whether recovery is needed. If a monitored Compose service is degraded, it runs the approved Docker Compose recovery path. It does not execute user-provided shell text.

### Pause Refresh

Stops automatic browser refresh. It does not stop the actual services. Resume Refresh starts automatic updates again.

### Download Diagnostics

Downloads the current health, service, offset, file, and log information as a diagnostic JSON bundle.

### Academic Viva Defense

Explains Kafka checkpoints, health-gated recovery, and partitioned Parquet in simple architecture terms.

## 12. Data honesty and limitations

- The parking telemetry is mainly generated for demonstration.
- Zone coordinates and the OpenStreetMap background are geographically meaningful.
- Open-Meteo can supply public weather context.
- OpenStreetMap can supply mapped parking-facility locations.
- Public services do not provide trustworthy live bay occupancy for this project.
- A real occupancy value must come from a sensor/Kafka event or an operator observation.
- Model results are forecasts, not guarantees.
- Estimated revenue and estimated drive time are demonstrations, not official values.
- If a service is offline, the interface should show offline/degraded or stored-snapshot wording instead of claiming that old data is live.

## 13. Suggested order for demonstrating the website

1. Start on **Overview** to explain the parking problem and current network state.
2. Open **Live Monitoring** to show Kafka events and Bloom-filter deduplication.
3. Open **Parking Map** to select a real Mumbai-area location and find an alternative hub.
4. Open **Historical Analytics** to explain long-term patterns.
5. Open **Demand Prediction** and compare all three models.
6. Open **Big Data Pipeline** to trace one event from sensor to dashboard.
7. Open **Data Explorer** to inspect schemas and stored records.
8. Finish with **System Health** to prove that the services and storage are working.

## 14. Short final explanation

Each page presents a different part of the same system. Live Monitoring shows events arriving. The Parking Map shows where those events belong. Historical Analytics explains past behaviour. Demand Prediction estimates future demand. The Big Data Pipeline explains how the event was processed. Data Explorer shows what was stored. System Health proves whether the supporting services are available. Overview combines the most important results into one control-room screen.
